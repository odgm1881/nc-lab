# НК-ЛАБ — Архитектура проекта (Этап 1)

Документ описывает архитектуру: подход, слои, структуру проекта, модель данных и
путь усложнения. Про конкретные технологии и версии — отдельный документ `STACK.md`.

Главный принцип: **делаем достаточно, но не больше.**

---

## 1. Философия: прагматично, а не «по учебнику»

Берём минимальный набор, который решает задачу, и проектируем так, чтобы
**сложность добавлялась позже точечно.** Модульный монолит легко разрезать на
сервисы, когда это реально понадобится.

Три правила:

1. Отделяем только то, что меняется. У нас это правила НК и разбор вариаций.
2. Одна база, один процесс, один деплой. Пока команда меньше пяти инженеров.
3. Каждую «умную» технологию добавляем под конкретную боль, а не заранее.

---

## 2. Архитектура: модульный монолит + прагматичные слои

**Модульный монолит.** Одно приложение, но внутри — независимые модули по бизнес-
смыслу: импорт, каталог, вариации, валидация, GTIN, РД, аутентификация. Модули
общаются через сервисы, а не лезут в таблицы друг друга напрямую.

**Прагматичные слои** внутри каждого модуля. Одна ценная идея из чистой архитектуры:
**бизнес-правила не должны зависеть от FastAPI и базы данных.**

По карте рисков главная угроза — изменения правил Нацкаталога. Если правила лежат
отдельным доменным слоем — правим один модуль и покрываем его тестами.

---

## 3. Слои и направление зависимостей

Зависимости идут только внутрь: веб знает о сервисах, сервисы знают о домене, домен
не знает ни о ком.

```
┌─────────────────────────────────────────────────────────┐
│  API-слой (FastAPI): роутеры, Pydantic-схемы, зависимости │
├─────────────────────────────────────────────────────────┤
│  Слой приложения / сервисы: сценарии, оркестрация          │
├─────────────────────────────────────────────────────────┤
│  Доменный слой (чистый Python): сущности, ядро правил      │
├─────────────────────────────────────────────────────────┤
│  Инфраструктура: SQLAlchemy-модели, репозитории, S3, API   │
└─────────────────────────────────────────────────────────┘
```

Правило команды: **если функцию можно протестировать без базы и без HTTP — она в
доменном слое.**

---

## 4. Организация по фиче, а не по типу файла

Верхний уровень делим на модули-фичи. Внутри модуля уже лежат его слои.

---

## 5. Структура проекта (бэкенд)

```
backend/
├── pyproject.toml
├── alembic.ini
├── docker-compose.yml
├── Dockerfile
├── migrations/               # Alembic
└── app/
    ├── main.py               # сборка FastAPI, подключение роутеров
    ├── config.py             # настройки через pydantic-settings
    ├── database.py           # engine, session, get_db-зависимость
    ├── core/                 # security.py, exceptions.py, storage.py
    └── modules/              # ← фичи. Сердце проекта.
        ├── auth/             # router, schemas, service, models, repository
        ├── import_data/      # router, schemas, service, parsers/, models
        ├── catalog/          # router, schemas, service, models, repository
        ├── variations/       # domain.py (чистая логика), service, schemas
        ├── validation/       # domain/{rules,registry,result}, service, schemas
        ├── gtin/             # domain.py (1 GTIN = 1 карточка), service, schemas
        ├── rd/               # domain.py (структура РД), service, schemas
        ├── operator/         # router, service, models (очередь задач)
        └── nk_exchange/      # порт, file/mock-адаптеры и журнал обмена
    └── tests/{unit,integration}
```

Доменные файлы (`domain.py`, `rules.py`) не импортируют FastAPI и SQLAlchemy.

## 6. Модель данных

### 6.1. Стратегия JSONB

**Фиксированные поля — колонками, изменчивые атрибуты категории — в JSONB.**

Карточка (`Card`):

```
id              UUID, первичный ключ
client_id       ссылка на клиента
category_code   код категории (ТН ВЭД / внутренний)
gtin            строка, уникальна в паре с вариацией
status          draft | validating | valid | error | published
attributes      JSONB — гибкие атрибуты категории
rd_data         JSONB — сведения о разрешительной документации
created_at
updated_at
```

Поле для поиска/джойна/уникальности — колонка. Поле, которое просто хранится и
валидируется по правилу категории, — в JSONB.

### 6.2. Статусы вместо очередей

На этапе 1 брокер сообщений не нужен. Состояние импорта и задач оператора храним
полем `status`. Обработку запускаем синхронно или через `BackgroundTasks` FastAPI.

## 7. Доменные модули

- **Импорт.** Парсер на каждый источник (Excel, CSV, 1С). Общий интерфейс: файл →
  список нормализованных строк. Файл в S3, факт загрузки — `ImportJob` со статусом.
- **Вариации.** Чистая логика: модель + оси значений → декартово произведение SKU.
- **Ядро правил (валидация).** Каждое правило — чистая функция card → список ошибок.
  Правила в реестре, легко пополнять.
- **GTIN.** Правило «1 GTIN = 1 карточка». Уникальность и формат (контрольная цифра).
- **РД.** Структура и полнота сведений о разрешительной документации до заказа кодов.
- **Консоль оператора.** Спорные карточки, очередь задач со статусами и приоритетом.
- **Обмен с НК.** Нейтральный версионированный контракт, файловый и mock-адаптеры,
  журнал операций, идемпотентность и ручной повтор. Боевой адаптер подключается к
  тому же порту после получения официального контракта и учётных данных.

---

## 8. Архитектура фронтенда

Старт — плоская структура (`api/`, `pages/`, `components/`, `types/`). Рост — модули
по фичам (`features/import`, `features/catalog`, …). Симметрия с бэкендом.

---

## 9. Чего НЕ делаем на этапе 1

Микросервисы, брокеры (Kafka/RabbitMQ), внешние очереди, Kubernetes, GraphQL,
ML/NLP в проде, мультитенантность на уровне схем БД, тяжёлый фронтенд-стек заранее.

---

## Итог

Модульный монолит с изоляцией доменной логики там, где это окупается: правила НК и
разбор вариаций. Фундамент закрывает три пилота и 300–500 карточек и оставляет
чистый путь к этапу 2: API НК, очереди и ML подключаются точечно.

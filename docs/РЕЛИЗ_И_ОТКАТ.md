# Релиз, staging и откат

## Перед релизом

1. Запустить `make check`.
2. На тестовой PostgreSQL выполнить `make migrations-check`.
3. Собрать образы: `make docker-build`.
4. Задать уникальный `APP_VERSION` и заполнить `.env.staging` по `.env.example`.
5. Создать резервную копию БД средствами облачного PostgreSQL или `pg_dump`.

Рекомендуемая команда проекта:

```bash
cd backend
DATABASE_URL="$DATABASE_URL" sh scripts/backup_postgres.sh
```

Скрипт создаёт дамп custom-format с правами `0600` и SHA-256 checksum. Каталог
backup не должен синхронизироваться в репозиторий.

## Staging

```bash
cd backend
docker compose \
  -f docker-compose.yml \
  -f docker-compose.staging.yml \
  --env-file ../.env.staging \
  up -d --build
```

После запуска проверить:

```bash
curl --fail http://localhost:8080/api/health/live
curl --fail http://localhost:8080/api/health/ready
```

Readiness считается успешным только при доступности и базы данных, и рабочего
файлового хранилища. Ответ содержит состояния обоих компонентов.

Staging-конфигурация не запускается с коротким/дефолтным JWT-секретом, SQLite,
открытым CORS или включёнными демо-аккаунтами. Демо-данные на staging не создаются.

## Откат

1. Остановить продвижение релиза и сохранить логи с `correlation_id`.
2. Вернуть предыдущие теги образов API и web.
3. Если миграция совместима назад, запустить предыдущие образы без отката БД.
4. Если миграция несовместима, остановить API, восстановить проверенную резервную
   копию в отдельную БД и переключить `DATABASE_URL`.
5. Проверить readiness и полный путь вход → каталог → валидация.

Не выполнять `alembic downgrade` автоматически в production: решение зависит от
конкретной миграции и риска потери данных. Для каждой несовместимой миграции в
описании релиза должен быть отдельный сценарий возврата.

## Обязательный тест восстановления

Создайте пустую отдельную БД, имя которой заканчивается на `_restore_test`, и выполните:

```bash
RESTORE_TEST_DATABASE_URL=postgresql://.../nklab_restore_test \
  sh backend/scripts/test_restore_postgres.sh backend/var/backups/nklab-....dump
```

Защита по суффиксу не позволяет случайно восстановить дамп поверх staging или
production. Тест проверяет checksum, восстанавливает схему и данные, затем проверяет
число таблиц и наличие версии Alembic. Результат теста и имя backup фиксируются в
релизном журнале. Не реже одного раза в месяц тест должен выполняться по расписанию.

## Обязательные проверки перед production

- вход, неуспешный вход и критичные действия присутствуют в журнале аудита;
- наблюдатель читает каталог, но получает 403 на создание и изменение карточки;
- импорт отклоняет расширения вне CSV/XLSX/XLSM/XML, повреждённый Excel, превышение
  размера архива и лимита строк;
- `/api/metrics` закрыт токеном, а мониторинг оповещает о росте 5xx и недоступности
  `/api/health/ready`;
- создан свежий backup с checksum и зафиксирован успешный тест восстановления;
- на staging выполнен полный путь: вход → импорт → валидация → пилот → пакет НК → сверка.

# Как НК-ЛАБ работает на самом деле

Честный технический разбор: что платформа делает, почему устроена именно так, и —
без прикрас — **что реально работает, что имитация, а чего нет вовсе**.

Про пользовательские сценарии — см. [`КАК-РАБОТАТЬ.md`](КАК-РАБОТАТЬ.md).

---

## 1. Зачем это всё (проблема)

Чтобы заказать коды маркировки на одежду, продавец сначала должен завести **карточку
товара в Национальном каталоге**. Карточка требует качества данных: обязательные
атрибуты, верный GTIN на каждую вариацию, подшитую разрешительную документацию (РД).

Боль клиента — не «получить код» (код стоит 61 копейку и выдаётся за секунды), а
**правильно описать товар до заказа кодов**. Цепочка **НК → GTIN → РД → коды** рвётся
в любом звене: нет РД — ввод в оборот отклонят; неверный GTIN — карточку пересоздавать
с нуля. Одна модель футболки в 5 цветах и 6 размерах — это 30 карточек, каждую нужно
описать без ошибок.

**Что делает НК-ЛАБ:** ловит эти ошибки заранее, на этапе описания, пока они дёшевы.
Не «печатает этикетки» — устраняет причину возвратов.

## 2. Как это устроено и почему именно так

### Архитектура: модульный монолит + изоляция домена

Одно приложение (FastAPI), внутри — независимые модули по фичам (`app/modules/`):
`auth`, `import_data`, `catalog`, `variations`, `validation`, `gtin`, `rd`, `operator`.

**Почему монолит, а не микросервисы?** Для 3 пилотов и 300–500 карточек микросервисы —
это недели работы и месяцы поддержки без пользы. Монолит легко разрезать на сервисы
позже; собрать микросервисы обратно в монолит — почти невозможно.

**Ключевое решение — доменная логика не зависит от FastAPI и базы.** Правила валидации,
разбор вариаций, проверка GTIN — это чистые функции Python (`domain.py`, `rules.py`).
**Почему:** по карте рисков главная угроза — изменение правил Нацкаталога. Если правила
вшиты в эндпоинты и модели БД, каждое изменение регулятора = переписывание приложения.
Отдельный доменный слой правится одной функцией и покрывается тестом за миллисекунды.

### Механизмы по отдельности

| Механизм | Как работает | Почему так |
|---|---|---|
| **Импорт** | Парсер на каждый источник (Excel/CSV/1С) → «сырые» строки → `map_row` приводит заголовки к каноническим полям по словарю синонимов. | Клиенты присылают файлы с разными заголовками. Синонимы («Артикул»/«Код»/«SKU») ловят это без ручной настройки. |
| **Вариации** | Декартово произведение осей `цвет × размер × пол × комплектность`. Чистая функция без БД. | Правило легпрома: каждая комбинация — отдельная карточка. Чистая функция тестируется тривиально и позже заменяется ML-нормализацией. |
| **Валидация** | Реестр правил; каждое правило — чистая функция `карточка → список замечаний` с кодом и severity (ERROR/WARNING). | При изменении требований НК добавляется одна функция и её тест, а не правка всего приложения. |
| **GTIN** | Проверка формата: длина 8/12/13/14 и **контрольная цифра по алгоритму GS1 (mod-10)**. Уникальность «1 GTIN = 1 карточка» — через `UNIQUE`-ограничение в БД + правило. | Ошибка в GTIN необратима, ловим до заказа кодов. |
| **РД** | Структурная проверка: известный тип (декларация/сертификат/отказное), заполнены номер и дата, не истёк срок. | Пробел в РД блокирует ввод в оборот уже после печати — проверяем заранее. |
| **Статусы вместо очередей** | Состояние карточки/импорта — поле `status` в Postgres (`draft → validating → valid \| error → published`). | На объёме 300–500 карточек брокер сообщений не нужен. `BackgroundTasks` FastAPI хватает. |
| **Хранение атрибутов** | Фиксированные поля (id, client_id, gtin, status) — колонками; изменчивые атрибуты категории и РД — в **JSONB**. | У десятков категорий одежды разный набор атрибутов. Таблица под каждую категорию — тупик. |
| **Аутентификация** | JWT: логин выдаёт токен, каждый запрос его проверяет; пароли — bcrypt. | Стандартно, без внешних зависимостей. |

## 3. Что реально работает, а что имитация

Это главный раздел. Без прикрас.

### ✅ Реально работает (не имитация)

- **Регистрация и вход** по JWT, роли клиент/оператор, хеширование паролей bcrypt.
- **Импорт Excel (.xlsx) и CSV** — файл реально парсится (openpyxl / csv), заголовки распознаются, строки нормализуются, создаются карточки в БД. Проверьте примером из `samples/`.
- **Построение вариаций** — реальное декартово произведение, создаёт N карточек.
- **Валидатор** — реально прогоняет карточку через все правила и возвращает конкретные ошибки:
  - обязательные атрибуты категории,
  - **контрольная цифра GTIN считается по-настоящему** (алгоритм GS1),
  - уникальность GTIN в пределах клиента,
  - смешение цвета/размера в одной карточке,
  - структура и срок РД.
- **Каталог** — CRUD карточек, фильтры, поиск, статусы — работают против реальной БД.
- **Консоль оператора** — очередь задач и список карточек с ошибками.
- **База данных** — PostgreSQL (JSONB) в Docker или SQLite локально; схема через миграции Alembic.
- **Тесты** — 48 автотестов (`uv run pytest`), доменная логика юнитами + API через httpx. Это можно запустить и увидеть зелёный прогон.

### 🟡 Имитация / упрощение (честно обозначаем)

- **«Опубликовать в НК»** — на этапе 1 это **смена статуса внутри платформы**, а не отправка в настоящий Национальный каталог. **Реальной интеграции с API НК / True API / СУЗ 3.0 нет** — это работа этапа 2 (см. дорожную карту в деке). Кнопка честно называется «Опубликовать», но никуда во внешнюю систему данные не уходят.
- **Проверка GTIN** — проверяется только **формат и контрольная цифра**. Соответствие GTIN реальному товару в реестре GS1 / базе ЦРПТ **не проверяется** (нет доступа к внешнему реестру).
- **Проверка РД** — проверяется **структура и полнота** сведений, а не подлинность документа в реестре ЦРПТ/Росаккредитации.
- **Онтология категорий** — это **прототип из 8 категорий ТН ВЭД** с базовым набором атрибутов одежды, а не полный официальный справочник атрибутов Национального каталога. Незнакомая категория проходит по базовому набору (с предупреждением).
- **S3-хранилище файлов** — если ключи S3 не заданы, файлы кладутся в **локальную папку** `var/storage`. Код для S3 есть, но по умолчанию работает локальный фолбэк.
- **Импорт «1С»** — поддержан как CSV-выгрузка с разделителем `;`. Полноценный обмен через XML/EnterpriseData — этап 2.

### ❌ Чего нет вовсе (намеренно отложено, этап 1)

Заказ кодов маркировки и печать этикеток · реальная интеграция с Честным ЗНАКом ·
таможня/СПОТ · ML/NLP-извлечение атрибутов в проде · очереди (Kafka/Celery) ·
микросервисы · Kubernetes · мультитенантность на уровне схем БД.

Это не «недоделки», а **явные границы этапа 1** (зафиксированы в `ARCHITECTURE.md §9`
и `CLAUDE.md`). MVP решает ровно одну задачу: **валидация карточек до заказа кодов**.

## 4. Итог: это честный MVP, а не витрина

Платформа **делает то, что заявляет для этапа 1**: принимает реальные файлы, строит
вариации, по-настоящему валидирует карточки (включая математику контрольной цифры GTIN)
и ведёт их по статусам — всё против реальной БД, с автотестами.

При этом мы **честно не притворяемся**, что уже интегрированы с государственными
системами: публикация в настоящий НК, заказ кодов, проверка документов в реестрах —
это следующий этап, и в интерфейсе/статусах это не выдаётся за готовое.

### Как убедиться самому

```bash
# backend/ — прогнать все тесты (доменные + API)
uv run pytest -q

# проверить контрольную цифру GTIN «руками»
uv run python -c "from app.modules.gtin.domain import is_valid_gtin; print(is_valid_gtin('4601000001002'), is_valid_gtin('123'))"
# -> True False

# проверить, что пример реально парсится
uv run python -c "from app.modules.import_data.parsers.excel import parse_excel; from app.modules.import_data.parsers.base import map_rows; print(len(map_rows(parse_excel(open('../samples/номенклатура-пример.xlsx','rb').read()))), 'строк')"
```

Живой прогон через API (импорт → валидация → публикация) описан в `README.md` и
воспроизводится на демо-данных (`uv run python -m app.seed`).
